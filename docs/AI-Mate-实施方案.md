AI Mate：一个月技术路线与工程实施方案

结合你的实际情况——基础编程水平、正在学习前后端开发、只有一个月左右——我建议把 AI Mate 定义为一个可运行、可验证、具备完整 Agent 执行闭环的 AI 任务协作系统。

这个月的目标不是做出一个什么都能做的通用智能体，而是做出一个真正能够完成以下流程的系统：

用户提出目标 → AI 制定计划 → 用户确认 → 系统执行任务 → 检查执行结果 → 根据反馈继续执行或调整计划 → 保存状态并恢复任务。

这条路线有两个原则：

* 先把单个 Agent 的执行闭环做可靠，再考虑多 Agent。
* 每一周都要交付一个能实际运行、能演示、能测试的成果。

一个月结束时，你应该拥有一个完整的全栈项目，而不只是一个聊天页面或者一张 AI 生成的任务流程图。

一、先确定 AI Mate 1.0 的技术目标

1. 产品范围

第一版聚焦一个明确场景：帮助用户完成有多个步骤、可以验证结果的数字化任务。

例如：

* 整理一份行业分析报告。
* 完成一个简单的网站开发任务。
* 研究某个技术主题并生成带来源的报告。
* 对一组文本或文件进行分类、整理和检查。

暂时不承诺自动完成所有现实世界任务，也不直接开放任意终端命令、任意文件操作或无限制的自主执行。

2. 必须实现的能力

任务规划

输入一个目标，生成结构化的任务列表、任务依赖和完成标准，支持人工修改。

工作流执行

按照依赖顺序执行任务，记录状态，处理失败、重试和用户审批。

状态持久化

保存任务、计划版本、执行记录和产物，服务重启后仍可恢复。

结果验证

使用规则、程序测试或用户审核确认任务完成，而不是直接相信模型的自我评价。

二、整体技术架构

我建议使用 TypeScript 贯穿前后端，减少你在一个月内切换多种语言和工具的成本。

前端：React + TypeScript + Vite

任务创建 · 任务地图 · 工作台 · 审批界面

后端 API：Node.js + Express

输入校验 · 业务逻辑 · 身份与权限 · 错误处理

Agent 服务

规划 · 工具调用 · 反馈处理

执行引擎

依赖 · 状态机 · 重试 · 暂停

SQLite

任务 · 状态 · 日志 · 产物

受控工具

报告生成 · 数据处理 · 校验

模型 API 是 Agent 服务调用的外部依赖。执行引擎负责控制流程，数据库保存事实状态，工具负责产生可观察的执行结果，验证器决定结果是否满足标准。

关键架构原则：不要让大模型直接控制数据库状态。 模型可以提出计划或工具调用请求，但必须由后端校验、执行并记录结果。

三、技术选型：哪些自己写，哪些使用成熟框架？

一个月时间，最怕的是一开始选了太多框架，最后一直在解决环境配置问题。

我建议采用以下方案。

组件	技术选择	为什么
前端	React + TypeScript + Vite	快速实现任务工作台
UI	Tailwind CSS	减少样式开发时间
后端	Node.js + Express + TypeScript	与前端使用同一种语言
数据校验	Zod	校验模型输出和 API 参数
AI 执行	OpenAI Agents SDK（TypeScript）	提供 Agent 循环、工具调用和追踪能力
工作流	自己实现轻量状态机	掌握核心控制逻辑，避免过度封装
数据库	SQLite + better-sqlite3	适合单机原型和本地持久化
测试	Vitest + Supertest	测试业务逻辑与 API
版本管理	Git + GitHub	记录开发进度和版本

OpenAI Agents SDK 支持 TypeScript、工具调用、人工介入与执行追踪，适合用来处理 Agent 的运行环节。

但任务状态机、任务依赖、重试规则和完成判定，建议由你自己实现。这些才是你理解 AI Mate 技术架构的关键。

官方文档：OpenAI Agents SDK（TypeScript）⁠

注意：如果你使用的模型服务不兼容该 SDK，就需要选择兼容的接入方式，或先用普通模型 API 实现同样的流程，不要让模型供应商成为整个项目的阻塞点。

五、数据库应该怎么设计？

不要把整个项目只保存成一段聊天记录。至少需要以下四张表。

表	作用	关键字段
projects	保存用户的目标项目	id、title、goal、status
tasks	保存每个子任务	id、project_id、title、status、dependencies
runs	保存每次执行记录	id、task_id、attempt、status、error
artifacts	保存生成的成果	id、task_id、type、content

另外，建议给 tasks 增加 plan_version 或建立单独的计划版本表，以便用户修改目标后能够追踪计划变化。

有两个重要的工程细节：

* 任务状态更新、执行记录和结果保存应尽量通过事务保证一致性。
* 恢复执行时，不能简单地把所有 running 任务重新执行，因为它们可能已经产生了外部副作用。

对于可能重复执行的操作，需要使用幂等设计或执行前检查。第一版可以只允许执行安全、可重复的工具，并把不能确认执行结果的任务转为待人工处理。

六、你应该深入研究的技术难题

你老师说这个方向深，真正能够体现技术理解的地方，就是你是否理解下面这些问题，以及能否用实验验证自己的设计。

难题 1：任务拆解的质量如何衡量？

模型能够生成任务列表，但怎样知道这份列表足够完整？

可以从任务覆盖率、依赖正确性、完成标准的可验证性和执行成功率等角度建立评价标准。

一个月内的做法： 准备 10—20 个有参考任务清单的测试案例，记录模型遗漏的步骤、错误依赖和无效任务。不要只凭主观感觉判断好坏。

难题 2：失败后应该重试还是重新规划？

网络超时、工具参数错误、任务依赖缺失和用户目标改变，不能全部用同一种方式处理。

建议区分：

* 暂时性错误：有限次数重试。
* 输入或参数错误：修正参数后再执行。
* 前置条件缺失：调整任务依赖或计划。
* 目标变化：重新规划受影响的任务。
* 需要用户决定：暂停并请求确认。

一个月内的做法： 手动构造几种故障，检查每种故障是否进入了正确的处理分支。

难题 3：如何确认任务真正完成？

模型可能生成一份格式完整、内容却不符合要求的报告。

解决方式不是让另一个模型简单地回答“是否合格”，而是结合多种验证方式：

* 结构和格式规则。
* 必需字段检查。
* 程序测试。
* 数据来源检查。
* 用户最终确认。

一个月内的做法： 为每种任务定义明确的验收条件，统计通过率和错误类型。

如果你希望将来进一步做研究，可以比较不同规划提示词、依赖建模方式或重试策略的表现。不过，第一阶段先把测量方法做扎实，比急着发明复杂算法更重要。

最后，怎么判断这一个月有没有成功？

我建议用一条完整的端到端测试作为最终标准：

用户输入“帮我整理一份技术主题报告”后，系统生成任务计划；用户修改并确认；系统调用工具完成资料整理和报告生成；验证器检查报告结构与必要内容；如果某项检查失败，系统根据错误进行修正或请求用户处理；最终保存报告、执行记录和任务状态。然后重启后端，仍然能够看到任务的最终状态和成果。

如果这条链路能够稳定运行，你就已经完成了一个具有真实 Agent 工程特征的项目。

这还不能说明你已经解决了通用 Agent 的所有难题，但足以成为进一步研究规划质量、动态重规划、记忆和多 Agent 协作的基础。

我最建议你坚持的顺序是：先完成任务闭环，再优化可靠性，最后研究高级机制。 不要为了让架构看起来复杂而提前引入多 Agent、向量数据库或复杂的自主执行能力。
