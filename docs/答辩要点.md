# AI Mate 答辩要点

> 配合 `docs/演示脚本.md` 使用。总时长建议 8~12 分钟：讲解 5 分钟 + 演示 3 分钟 + 提问 3 分钟。

## 0. 开场（30 秒）

> AI Mate 不是一个聊天框，而是一个**可运行、可验证、具备完整 Agent 执行闭环**的任务协作系统。
> 核心链路是：目标 → 计划 → 用户确认 → 程序执行 → 验证器判定 → 持久化与恢复。
> 关键原则有两条：**模型不直接改状态**，**完成与否不采信模型自评**。

## 1. 难题一：任务拆解的质量如何衡量？

### 回答框架（先给指标，再给方法）

**四个可量化指标：**

| 指标 | 定义 | 怎么算 |
|---|---|---|
| 任务覆盖率 | 参考计划中的必要步骤被覆盖的比例 | 命中步骤数 / 参考步骤数 |
| 依赖正确性 | 依赖边正确的比例 | 正确的依赖边 / 标注依赖边 |
| 完成标准可验证性 | 有具体可检查标准的任务占比 | 可验证任务数 / 总任务数 |
| 执行成功率 | 计划落库后能被执行器跑通的任务占比 | succeeded 任务 / 总任务 |

**测量方法（一个月内可落地）：**

1. 准备 **10~20 个带参考计划的目标**（例如"整理 XX 技术报告""对比 3 个开源项目"），人工标注参考任务清单与依赖
2. 对每个目标重复生成 N 次（如 5 次），统计上述指标
3. 错误分类记录：**遗漏步骤 / 错误依赖 / 无效任务 / 标准空泛**
4. 形成表格：`目标 × 指标 × 提示词版本`，用于对比不同 prompt / temperature

**本项目的埋点已经具备：**

- `plan_versions.raw_output` 保存模型原始输出（可回放评测）
- `tasks` / `runs` 保存落库结果与执行情况（可直接算执行成功率）
- `services/planRules.ts` 已能区分 `PLAN_INVALID / PLAN_DEPENDENCY / PLAN_CYCLIC`，可统计错误类型分布

**如果追问"你怎么知道参考计划是对的？"**
→ 由人工标注，并做**双人标注一致性**检查（不一致的案例讨论后修订），承认这是主观性来源，但可复现。

## 2. 难题二：失败后该重试还是重新规划？

### 核心答案：先分类，再决定

| 失败类型 | 典型表现 | 策略 |
|---|---|---|
| 暂时性错误 | 网络超时、服务 5xx、限流 | **有限重试**（指数退避） |
| 输入/参数错误 | 工具参数不合法、格式不符 | **修正参数后重试**（不盲目重试） |
| 前置条件缺失 | 依赖任务未完成 / 缺失数据源 | **调整依赖或计划** |
| 目标变化 | 用户改了目标 | **重新规划受影响任务** |
| 需要用户决定 | 涉及发布/删除/付费、验证不通过需人工判断 | **暂停并请求确认** |

### 本项目的实现映射

- `tasks.max_attempts`（默认 3）+ `attempts`：限制重试次数
- `tasks.last_error` + `runs.error`：保留失败原因，供决策
- 重试耗尽 → 任务 `failed`，项目 `failed`，**不会无限重试**
- 前端提供两个明确入口：**「重试失败任务」**（沿用原计划）与 **「重新规划」**（重新生成计划，版本 +1）
- 需审批/需人工判断 → 任务 `needs_review` + 项目 `awaiting_confirmation`，等待人批准
- 模型侧：`planner.ts` 对超时/网络失败**自动重试 1 次**，仍失败返回 502，不污染数据库

**怎么演示：**
- 暂时性错误：把 `MODEL_BASE_URL` 改成不可达地址 → 502 + 服务不崩
- 验证失败：把某任务依赖内容改成含 `TODO` → `text_check` 失败 → 重试到上限 → failed
- 审批分支：勾选"需人工审批" → 执行暂停 → 批准后继续

## 3. 难题三：如何确认任务真正完成？

### 核心答案：多源验证，不采信模型自评

| 验证层 | 本项目做法 |
|---|---|
| 结构与格式规则 | 报告必须有 `#` 标题 + ≥2 个 `##` 章节；长度阈值 |
| 必需字段检查 | 每个任务必须有 `acceptance_criteria`，为空直接判失败 |
| 程序化检查 | `text_check` 解析 JSON 并检查 `ok === true`；检测 `TODO / 待补充 / Lorem` 等占位内容 |
| 数据来源检查 | 任务声明依赖的前置产出必须存在且被实际读取（依赖顺序 + 输出传递）|
| 用户最终确认 | 需审批任务暂停等待人批准；项目层确认后才开始执行 |

**为什么不用"另一个模型判断是否合格"？**
- 不可复现、成本翻倍、判定标准漂移
- 要求"可验证"就必须落到**可执行的规则**上；模型只能辅助生成规则，不能作为最终裁决

**可以给出的数据：**
- 每类任务的验收条件 = `acceptance_criteria` + 验证器规则
- 执行记录 `runs` 里保留 verdict 失败原因（`issues.join('；')`）
- 可统计：一次通过率、重试后成功率、失败类型分布

## 4. 架构与选型追问

| 问题 | 回答要点 |
|---|---|
| 为什么不用 Dify / n8n / LangGraph？ | 作业要求自研状态机、依赖与验证逻辑；现成平台改造成本高、也很难讲清"我设计了什么"。我们只借鉴了 checkpoint 与 runs 记录的思路 |
| 为什么用 SQLite？ | 单机原型足够、零部署、事务可靠；`node:sqlite` 免原生编译。多实例时再换 Postgres |
| 为什么自研状态机而不是让模型决定？ | 可审计、可复现、可测试；模型只提计划与工具请求 |
| 模型能直接改数据库吗？ | **不能**。计划与工具结果都要经 Zod 校验，状态由 `executor.ts` 在事务里写入 |
| 单机并发怎么处理？ | 执行器用内存锁防同项目重复执行；状态变更在事务中完成；多实例需分布式锁 |
| 重启后任务怎么办？ | `running` 可能已有外部副作用 → 统一转 `needs_review`，**不盲目重跑** |
| 重试会不会重复副作用？ | 当前工具都是**确定性、幂等**的（生成报告/检查文本）；有副作用的工具需幂等键或人工确认后再执行 |
| 密钥安全？ | `.env` 被 gitignore，仓库只提交 `.env.example`；已验证远程仓库无 `.env` |
| 怎么保证前后端状态一致？ | 状态只存数据库，前端每次操作后重新拉取；`/health` 暴露四表计数与 schema 版本 |
| 测试怎么做的？ | Vitest + Supertest；`:memory:` 数据库隔离；50 个用例覆盖 CRUD、状态机、计划解析、执行器、审批、重试、恢复、模型失败兜底 |

## 5. 三分钟演示脚本（精简版）

1. 打开 http://localhost:5173，指出顶部「后端在线 / 模型已配置」
2. 新建项目 → 「用 AI 生成计划」→ 展示 6~8 个任务、依赖、完成标准
3. 「编辑计划」→ 给最后一个任务勾「需人工审批」→ 保存（状态：待用户确认）
4. 「确认执行」→ 任务逐个变绿 → 停在审批任务（待人工复核）
5. 「批准并继续」→ 项目 done
6. 切「任务地图」→ 指出分层与箭头；点节点看详情/执行日志/产物
7. 打开 `/health` → 展示 schemaVersion=3 与四表计数
8. 收尾：`npm test` 50 个用例通过
